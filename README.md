# 🛡️ Anti-Scam Trainer

Интерактивный тренажёр безопасных сделок для пользователей Avito. Кейс 5 хакатона **Avito Start**.

## Проблема

На классифайдах пользователи договариваются о сделках напрямую и сталкиваются с типовыми схемами мошенничества: переход в сторонние мессенджеры, фишинговые ссылки на «безопасную оплату», запрос кода из SMS, предоплата вне платформы. Платформа может бороться с мошенничеством технически, но часть безопасности всегда зависит от решений самого пользователя — и обычные текстовые инструкции работают хуже, чем практика.

## Решение

Веб-приложение — интерактивный тренажёр, в котором пользователь выбирает роль (покупатель/продавец), проходит реалистичные диалоговые сценарии сделок, принимает решения в спорных моментах и получает объяснение последствий каждого выбора — не просто «правильно/неправильно», а почему решение повышает или снижает риск.

### Backend
- **Go 1.25**, стандартный `net/http` (роутер на паттернах Go 1.22+)
- PostgreSQL – выбран из-за транзакционных гарантий при атомарной записи ответа, перехода, результата попытки и награды; реляционные ограничения и индексы защищают инварианты, а JSONB позволяет хранить версионируемый граф сценария

## Быстрый старт

### Через Docker Compose (рекомендуется — поднимает весь стек)

1. Скопируй `.config.example.yaml` в `config.yaml` и заполни значения:
   ```bash
   config.example.yaml
   ```
2. Подними:
   ```bash
   docker compose up --build -d
   ```
3. Открой:
   - Frontend: http://localhost:3000
   - Backend health-check: http://localhost:18080/health

4. Останови:
   ```bash
   docker compose down
   ```

### Backend отдельно (для разработки)

```bash
docker compose up postgres -d
cd backend
go run ./cmd/api --config config.yaml
```

### Frontend отдельно
*[ЗАПОЛНИТЬ: команды запуска фронтенда в dev-режиме]*
```bash
cd frontend
npm install
npm run dev
```

## API

Контракт эндпоинтов – [`backend/openapi.yaml`](backend/openapi.yaml) (OpenAPI 3.0, открывается в Swagger Editor или импортируется в Postman).

### Auth
| Метод | Путь | Описание |
|---|---|---|
| POST | `/api/v1/auth/register` | Регистрация |
| POST | `/api/v1/auth/login` | Вход (устанавливает HttpOnly cookie сессии) |
| POST | `/api/v1/auth/logout` | Выход |
| POST | `/api/v1/auth/forgot-password` | Запрос на восстановление пароля (email) |
| POST | `/api/v1/auth/reset-password` | Сброс пароля по токену из письма |
| GET | `/api/v1/users/me` | Текущий пользователь (требует авторизации) |

### Сценарии и попытки
| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/v1/scenarios?role=buyer\|seller` | Каталог сценариев для выбранной роли |
| POST | `/api/v1/scenarios/{scenarioID}/attempts` | Начать новую или продолжить активную попытку |
| GET | `/api/v1/scenarios/{scenarioID}/attempts/active` | Получить активную попытку сценария |
| POST | `/api/v1/scenarios/{scenarioID}/attempts/restart` | Прервать активную попытку и начать новую |
| GET | `/api/v1/attempts/{attemptID}` | Получить текущее состояние прохождения |
| POST | `/api/v1/attempts/{attemptID}/answers` | Сохранить выбор и выполнить переход по сценарию |

### Система
| Метод | Путь | Описание |
|---|---|---|
| GET | `/health` | Процесс жив |
| GET | `/ready` | Готовность (проверка соединения с БД) |

## Особенности реализации

- **Сессии** — opaque-токены (UUID) в HttpOnly cookie, не JWT: логаут = удаление записи из БД, простая инвалидация.
- **Пароли** — bcrypt, минимум 8 символов.
- **Восстановление пароля** — одноразовый криптографически случайный токен (`crypto/rand`), хранится в БД только в виде SHA-256 хэша, TTL 1 час.
- **CORS** — явный allowlist origin'ов с `Access-Control-Allow-Credentials`, без wildcard (требование безопасности при работе с cookie).
- **Сценарный движок** – детерминированные переходы по валидированному графу; любой путь завершается одной из объявленных концовок.
- **Идемпотентность ответов** – повтор запроса с теми же ключом и payload возвращает прежний результат; конфликтующий повтор или второй выбор для узла завершается `409 Conflict`.
- **Атомарность прохождения** – ответ, переход, итоговый score, завершение попытки и выдача фрагмента пазла сохраняются одной PostgreSQL-транзакцией.
- **Версионирование сценариев** – метаданные хранятся в реляционных колонках, граф – в JSONB; seed-loader строго валидирует и идемпотентно загружает четыре сценария при запуске backend.
